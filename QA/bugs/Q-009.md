# Q-009 · 仓库根缺 `.gitattributes`，根目录二进制与 CSV 的行尾/二进制属性不受管

- 严重度：P2（资产入库安全性 + 仓库整洁度）
- 发现者：Q1（2026-10-28 干净克隆验证）
- 状态：待修
- 依赖票：无
- owner：D3 / P0
- 证据报告：`QA/reports/2026-10-28-review.md` §6.2 / §6.5

## 现象

`.gitattributes` 放在 **`Juhuo/` 子目录**里：

```
$ ls .gitattributes
ls: cannot access '.gitattributes': No such file or directory
$ ls Juhuo/.gitattributes
-rw-r--r-- 1 qwert 197609 1676 ... Juhuo/.gitattributes
```

git 的 `.gitattributes` **只对所在目录及其子目录生效**。
因此 `Juhuo/.gitattributes` 里的规则（`*.csv text eol=lf`、`*.png -text`、`*.ttf -text` 等）
**完全管不到仓库根的文件**。

## 复现步骤

```bash
$ git check-attr text eol -- "举火_文本表_v1.0.csv"
"举火_文本表_v1.0.csv": text: unspecified
"举火_文本表_v1.0.csv": eol: unspecified

$ git check-attr text eol -- "举火_序章数据_全关卡_v1.1.csv"
...: text: unspecified / eol: unspecified

$ git check-attr text eol -- "举火_序章数据_白幡村_v1.0.csv"
...: text: unspecified / eol: unspecified
```

## 期望

仓库级 `.gitattributes` 覆盖全仓；所有二进制显式标 `-text`；所有需要固定行尾的文本显式声明。

## 实际

仓库根**完全没有属性约束**，受影响的是：

| 类别 | 文件 | 现状 |
|---|---|---|
| 二进制 | `onboard_1.png`、`onboard_exit.png`、`onboard_help.png`、`onboard_talk.png`、`palette_preview.png`（共 1.4 MB）、**`100`**（348 B PNG） | 无 `-text` 保护（实测当前**未损坏**，见「影响面」） |
| 源 CSV | `举火_文本表_v1.0.csv`、`举火_序章数据_全关卡_v1.1.csv`、`举火_序章数据_白幡村_v1.0.csv` | 行尾不锁定，实测入库为 CRLF（`举火_文本表_v1.0.csv` CR=241 / LF=241） |

> 对照：`Juhuo/` 下的同类文件属性正常，例如
> `git check-attr text eol -- Juhuo/Content/data/npcs.csv` → `text: set` / `eol: lf`。

## 附带发现：仓库根有一个名为 `100` 的垃圾文件

```bash
$ git ls-files | grep -E "^100$"
100

$ python -c "d=open('100','rb').read(); print(len(d), d[:8])"
348 b'\x89PNG\r\n\x1a\n'
```

- 348 字节的 PNG，文件名就叫 `100`。
- 随基线提交 `3277bc5` 入库：`git log --oneline --diff-filter=A -- 100` → `3277bc5 baseline: ...`
- **全仓无任何引用**：`grep -rn "\"100\"\|'100'" tools/*.py Juhuo/Src/` 无命中。

显然是一次误提交（大概率是某个命令把输出重定向到了 `100`）。

## 影响面

**先说实测结论（避免夸大）**：我用 `core.autocrlf=true` 的空仓库实测了「无 `.gitattributes`」时的检出行为：

```
PNG IDENTICAL（git 自动识别二进制，未损坏）
CSV: source CR=241 LF=241 → checkout CR=241 LF=241（未变）
```

即：**PNG 不会被 `autocrlf` 损坏**（git 靠内容嗅探识别二进制），**根目录 CSV 在检出时也没被转成 CRLF**
（因为 blob 里本来存的就是 CRLF，转换是幂等的）。

所以本条**不是「资产会损坏」的隐患**，而是：

1. **根目录文件不受任何显式属性保护**，当前安全是靠 git 的内容嗅探与 `autocrlf` 的幂等性，
   **不是靠规则**。一旦某个根目录文件被误判为文本（例如改成 `.txt`、或内容恰好没有 NUL 字节），
   就没有 `-text` 兜底。
2. **源 CSV 行尾不锁定**：根目录 3 个 `举火_*.csv` 的行尾取决于入库时机器的 `autocrlf` 设置。
   本机入库时是 CRLF（实测 CR=241/LF=241）。若换一台 `autocrlf=input` 或 `false` 的机器重新入库同一内容，
   blob 会变 LF，**产生一次全文件 diff**。源 CSV 是生成脚本的输入，diff 噪音会干扰内容比对。
3. **`100` 是无用文件**，应在 G0 前清掉。
4. 与 `Juhuo/.gitattributes` 形成**双份规则源**：一份在 `Juhuo/`（管用），一份缺失（根目录不管用）。
   将来有人改 `Juhuo/.gitattributes` 时会以为全仓生效，实际根目录不受影响 —— 这就是 Q-006 那类问题的温床。

## 修复建议

1. 在**仓库根**加 `.gitattributes`，把 `Juhuo/.gitattributes` 的规则上提（或根目录一份完整版，
   `Juhuo/` 那份保留或删除，二选一，别两份内容漂移）：

   ```gitattributes
   # 文本
   * text=auto eol=lf
   *.cs      text eol=lf
   *.csproj  text eol=crlf
   *.sln     text eol=crlf
   *.md      text eol=lf
   *.csv     text eol=lf
   *.tscn    text eol=lf
   *.tres    text eol=lf
   *.godot  text eol=lf

   # 二进制
   *.png      -text
   *.jpg      -text
   *.aseprite -text
   *.psd      -text
   *.wav      -text
   *.ogg      -text
   *.mp3      -text
   *.ttf      -text
   *.otf      -text
   ```

2. 删除 `100`：

   ```bash
   git rm 100
   ```

3. 根级 CSV 加完后做一次归一（与 Q-006 同理）：
   `git add --renormalize .`

## 验收

```bash
$ git check-attr text eol -- "举火_文本表_v1.0.csv"
"举火_文本表_v1.0.csv": text: set
"举火_文本表_v1.0.csv": eol: lf

$ git ls-files | grep -E "^100$"   # 应无输出
```

## 备注

- 与 Q-006 是**两个独立的问题**：Q-006 是"`Juhuo/` 下规则生效了但存量没归一"，
  本条是"根目录压根没有规则覆盖"。修 Q-006 时把归一范围扩到全仓，可以一并处理根目录 CSV。
- `Juhuo/.gitattributes` 里的 LFS 规则已由提交 `38b09be` 整体去掉（原因：本机没有 git-lfs，
  带 LFS 规则的文件在无 git-lfs 的机器上检出直接失败）。本条**不要把 LFS 规则加回来**。
