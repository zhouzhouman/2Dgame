# Q-011 · 协作方案里的冲突记录原文未随 README 同步

- 严重度：P3（文档口径不一致，误导后续 agent）
- 发现者：Q1（2026-10-28 复核 P0 基线报告 §3）
- 状态：待修
- 依赖票：无
- owner：P0（`举火_多智能体开发协作方案_v1.0.md` 属 P0 所有，见 CANON §7）
- 证据报告：`QA/reports/2026-10-28-review.md` §3.2

## 现象

基线报告 §3 第 2 条记录了这样一条冲突：

> 单测：README 结构图写 7 个、正文写 16 个 → 以 `dotnet test` 为准，**README 已改**

README 确实改了（`Juhuo/README.md:103` 现为 `xUnit（16 个测试）`）。
但**引用这个旧冲突的原文**在协作方案里没同步：

```bash
$ grep -n "7 个" 举火_多智能体开发协作方案_v1.0.md
148:| 3 | 单测数量 | README 表格"7 个" | README 正文"16 个" | **以 `dotnet test` 为准** |
```

## 复现步骤

1. `grep -n "7 个" 举火_多智能体开发协作方案_v1.0.md` → `:148`
2. `grep -n "xUnit" Juhuo/README.md` → `:103  xUnit（16 个测试）`
3. 对比即知：协作方案仍把"README 表格写 7 个"当作**当前事实**描述。

## 期望

冲突已在 README 侧解决后，协作方案里的冲突记录应同步标注"已解决"或改写，
避免后续 agent 读到后以为冲突仍然存在、进而重复处理。

## 实际

协作方案第 148 行仍以现状口吻描述旧冲突，未标状态。

## 影响面

1. **协作方案是"多智能体开发协作方案"，正是各 agent 开工前读的文件。**
   CANON §5 定的效力顺序是「CANON > 设定决策日志 > 设计文档 > 专项文档 > 代码注释 > agent 记忆」，
   协作方案虽未单列，但作为专项文档排在设计文档之后。
2. 后续 agent 读到 `:148` 可能误判"单测数冲突未解决"，做无用功，
   或更糟：**为了对齐"表格里的 7 个"而把 README 改回 7 个**。
3. 严重度定 P3：不影响代码，不影响当前 CI，不影响任何已验证的数字（真实值就是 16，
   两条 grep 与 `dotnet test` 都能确认）。

## 修复建议

改 `举火_多智能体开发协作方案_v1.0.md:148`，加上状态标记，例如：

```
| 3 | 单测数量 | README 表格"7 个" | README 正文"16 个" | **以 `dotnet test` 为准**（已解决：README 已统一为 16，见 584f862） |
```

或在该表下方加一行说明："以上冲突 1~7 已于 2026-10-28 全部裁定并落 README / 索引，见 DECISIONS D-001~D-011"。

## 验收

```bash
$ grep -rn "7 个\|22 位\|23 位" *.md Juhuo/README.md
# 应无任何一条仍在以现状口吻描述已解决的冲突
```
